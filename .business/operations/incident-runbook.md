# Incident Runbook

> Скелет. Расширять при каждом реальном инциденте.

## Принципы

1. **Сначала остановить кровь**, потом разбираться.
2. **Коммуникация прозрачная**: status page (`/status`) даже если pretend.
3. **Постмортем обязателен** для P0/P1 — складываем в `history/incidents/YYYY-MM-DD-name.md`.
4. **Никаких `--no-verify` / `--force`** в проде. Лучше откат.

## Severity

| Уровень | Что | Время реакции |
|---|---|---|
| P0 | Прод упал, юзеры не могут зайти | <15 мин |
| P1 | Существенная фича не работает | <2 ч |
| P2 | Косметическая ошибка / медленно | <24 ч |
| P3 | Минорное наблюдение | следующий релиз |

## Типовые сценарии

### Backend упал (5xx на /health)

1. Проверить Yandex Cloud Status — может это инфра
2. Проверить логи: `tail -f /var/log/atom/app.log` — ищем traceback
3. Если deploy был только что — откат: `kubectl rollout undo` или ручная замена
4. Если нет — restart сервиса
5. Постмортем

### БД медленно

1. `pg_stat_activity` — текущие запросы
2. `EXPLAIN ANALYZE` для подозрительных
3. Проверить индексы (особенно после миграций)
4. Если N+1 в коде — фикс + cache hotfix

### MOEX API упал

1. Сервис продолжает работать — все вызовы идут с retry+jitter
2. Проверить `iss.moex.com` — внешняя зависимость
3. Если долгое падение — отключить MAE/MFE автоматический пересчёт (через feature flag)
4. Сообщить юзерам через баннер

### Skell-блокер: «нет SECRET_KEY»

В проде backend упадёт на старте если SECRET_KEY не задан (см. `config.py:_resolve_secret_key`).
Это **защита**, не баг. Восстановить из Yandex Lockbox и перезапустить.

### Нагрузка на ЮKassa webhook

Если шторм входящих платежей:
1. Идемпотентность по `external_id` — повторы не создают дублей
2. Но процессинг medium-долгий — нужно делать BackgroundTask или Celery
3. Если падает — webhook возвращает 5xx, ЮKassa повторит
