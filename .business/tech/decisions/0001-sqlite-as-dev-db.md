# ADR-0001: SQLite как dev-БД, Postgres только для прода

**Статус:** Принято
**Дата:** 2026-05-07
**Контекст PR:** Аудит на 33 метрики, ответ на Q5 «PostgreSQL — режим работы»

## Контекст

В `backend/config.py:161` — `DATABASE_URL` по умолчанию `sqlite:///./atom.db`. В `docker-compose.yml` есть готовая конфигурация под Postgres 16, но Docker на машине разработчика не установлен. В существующей `atom.db` (~300 КБ) уже есть данные (видны на скриншотах Trade Replay — реальные свечи LKOH).

## Решение

**Оставить SQLite для dev, Postgres переключаем env-переменной `DATABASE_URL` когда:**
- Установлен Docker Desktop, или
- Подключён Yandex Managed Database, или
- Появится второй разработчик (SQLite не очень для concurrent writes), или
- Запускаем нагрузочные тесты

PostgreSQL MCP **НЕ подключаем** пока живём на SQLite.

## Последствия

**Плюсы:**
- Нулевой setup для dev
- `.db` файл версионируется через git (или volume в docker)
- Все 363 теста проходят на SQLite
- Alembic миграции работают через `batch_alter_table` (для SQLite-совместимости ALTER COLUMN)

**Минусы / риски:**
- Нет concurrent-write нагрузки в dev — баги могут вылезти только в prod
- `JSON` тип в SQLite — текстовое поле, нет нативных операторов JSONB. Все JSON-запросы пишем в Python-коде, не в SQL.
- Решение откладывается, не отменяется — миграция на Postgres неизбежна

## Поведенческие правила

1. Все ALTER TABLE миграции пишем через `op.batch_alter_table(...)` — без этого SQLite ломается.
2. `inspector.has_table()` / `inspector.get_columns()` для идемпотентности (см. `0002_add_pd_consents.py` как эталон).
3. При запуске alembic — **строго** из `cd backend/`, иначе относительный путь `./atom.db` создаст пустую БД в неправильной cwd.
4. Не использовать SQLite-специфичные фичи (FTS5, JSON1 функции) — нужно работать и в Postgres.

## Когда пересматривать

- Появление второго разработчика
- Подключение реальных пользователей (>100)
- Падение dev-БД на race condition
